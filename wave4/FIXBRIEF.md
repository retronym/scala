# Wave four: rules for fix workers

Read `/Users/jzaugg-virtus/code/.worktrees/scala/bug-hunting-second-wave-da4ba4/wave2/FIXBRIEF.md` fully first, then `wave3/FIXBRIEF.md` beside it: their rules, deliverable files and report format apply. This file says what differs for wave four. Where they disagree, this one wins.

- **Mode: fix where clear cut.** The owner asked for fix pull requests, not test-only ones. Work as in the wave-two section "Batches of findings": per finding, write the test first and see it fail, then fix at the root cause where the fix is clear cut; where it is a design question or does not converge in about 30 minutes, the branch holds the failing test alone and the body gives the options (outcome DESIGN or STUCK). Use the review's `fixability` as the starting judgment and wave three's rule that compatibility is part of "clear cut".
- **Findings and reviews** are under `wave4/findings/<ID>/` and `wave4/reviews/<ID>.json` in `/Users/jzaugg-virtus/code/.worktrees/scala/eager-jackson-1fc898`. Where the review corrects the hunter, the review is the better guide. A finding the review judges `wrong`, `by design` or `duplicate of` another gets no branch: write `result.json` with outcome NOT REPRODUCED or COVERED and the reason.
- **Base commit**: `4a67cb8202` (the fork's `2.13.x`). Every branch is `review/w4-<id in lower case>-<short-slug>` from that commit, one commit, one finding.
- **Workspace**: named in your brief; an APFS clone of a warm build at an older commit (`713241d26f`) on a throwaway branch. The first compile after checking out a branch from the base recompiles reflect and the compiler once, several minutes; keep one sbt session's worth of work per run and batch tasks. Three other workers build at the same time: at most one sbt at a time per worker, `sbt -java-home ~/.sdkman/candidates/java/21.0.12+1.1-tem`, bgrun for anything over five minutes, and `df -h /` before each build (under 5 GB free: stop and report DISK FULL). The launcher scripts under `build/` in a clone point at the golden build, as the wave-three file explains; run tests through sbt (`junit/testOnly`, `partest`).
- **Tests**: library findings get JUnit tests under `test/junit` in the existing test class for the type; compiler findings a partest (`run`, `pos`, `neg`; a directory holding `.java` and `.scala` files is compiled jointly; `//> using jvm 17+` for records and sealed types). Show the test failing before the fix and passing after, and run the neighbouring tests of the area. Library changes: `library/mimaReportBinaryIssues`.
- **Stacking**: where the review says the right outcome is a wider fix on an existing fork pull request, do not touch that pull request's branch. If your fix can only be written on top of it, branch from that pull request's head (`git fetch origin pull/<n>/head`) with one commit of your own, record `stacked_on` in `result.json` and say in the body's first paragraph that it is stacked on `retronym/scala#<n>`. Otherwise branch from the base and name the related pull request in the body.
- **Deliverables** go in `wave4/fixes/<ID>/` (`result.json`, `pr-title.txt`, `pr-body.md`), same fields as wave two, `workspace` an absolute path. The pull-request body's closing line is exactly: `Found in the fourth wave of the coordinated code review of 2.13.x (finding <ID>). Prepared with Claude.`
- **Pull-request body**: for a fix: problem, mechanism, fix, for a busy expert. For a test-only branch the first paragraph says the pull request holds a failing test and no fix. In both: what the program does, what it should do and why, the mechanism and code location as far as the finding and its review establish them, whether it is a regression (name the upstream pull request if the review found it), existing tickets and related pull requests on the fork (qualified, `retronym/scala#NNN`), and a short "possible fix" paragraph. Do not say how the defect was found beyond the closing line, no generator or seed, no testing status, no counts, no commit SHAs, no manual line wrapping.
- The fork's CI runs on JDK 8 with fatal warnings: no unused imports or values in tests, no Java 9+ API without the `jvm` line.

## Rework after diff review

A diff reviewer read each fix pull request; its verdicts are in `/Users/jzaugg-virtus/.claude/scala-2-13-review-dashboard/diffreview-w4-*.json`, keyed by pull-request number. In rework mode your brief lists pull requests whose verdict is `defect` or `concern`. For each:

- Do not check out or amend the pull request's branch: another worker created it. Create `sweep/<the branch name without review/>` at that branch's head (`git fetch -q origin <branch>` then `git checkout -b sweep/... FETCH_HEAD`), make the change, and amend so the sweep branch is one commit on the same base as before, holding test and fix. The coordinator pushes it over the pull request's head.
- Add a test for each input the reviewer gave, and reproduce each on the unreworked branch first.
- Rewrite `result.json` (`branch` is the sweep branch, add `sweep` with value `"review-fix"`), `pr-title.txt` and `pr-body.md` in `wave4/fixes/<ID>/`. The body describes the change as it now stands, with no account of the rework.
- If a reviewer's point is a decision for the owner and not a defect, do not decide it: state the options in the body.
