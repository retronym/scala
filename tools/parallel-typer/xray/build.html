Pipelined Build Scaling

How should a clean build of a multi-module Scala project spend its cores, now that a compile can use more than one? Real builds of ScalaTest, compiled in one JVM, checking a simulator's predictions.

What was found

Two directions to scale

A split M×T runs up to M compiles at once on T threads each. Those are the sides of a rectangle whose area is the threads it uses. Each direction hits its own limit, so a long thin rectangle wastes much of its area, and the same threads get further as a square.

Premise

A multi-module build can spend its cores in two ways. It can run as many modules at once as it has cores, each on the serial compiler. Or it can run fewer modules and give each several typer threads with -Yparallel-typer. Pipelining adds a third lever: a module can start as soon as its dependencies have written their pickles, without waiting for their class files.

A simulator built from single-corpus scaling curves made three claims about 8 cores. Real module graphs put 23–43% of their code in one module, so 8 serial compiles at once reach only 1.7–2.9×, while one parallel compile at a time reaches 4.6–4.8×. Mixed splits such as 2×4 do at least as well on some graphs. And moving workers to the modules others wait on adds 5–21% where chokepoints hold 10% or more of the work.

Those are estimates: warm JITs, workers that move instantly, module times taken from line counts. This experiment runs the real thing and measures how far off the simulator is.

Experiment design

The subject is ScalaTest, chosen because it is real code, macro-heavy, and large once its generated tests are counted: . Each measurement is a complete clean build in one warm JVM with no incremental compiler.

What varies

The splits cover three budgets. One thread is the serial baseline that speed-ups are measured against. Eight threads tests the simulator's claims, and sixteen shows what happens with twice as many; 3×5 uses 15, the closest three compiles can get to 16 with equal threads. A budget caps the compiler's threads. It does not pin them to cores: this machine has 18, and ParallelGC's 14 threads run on top of the budget.

What stays fixed

  • Patched JDK 26, ParallelGC, 31 GB heap with a 20 GB young generation and ParallelGC's adaptive survivor sizing, compressed oops on. All parallel phases on.
  • Three warm-up builds, then every token in a different order each round, three rounds, in one JVM. The collector's sizing carries over between tokens, and it made one token 60% slower in an earlier run, so shuffling spreads that effect across tokens and the ranges show it. Turning adaptive sizing off is worse: the old generation fills and a single full collection takes up to 33 s.
  • Each measurement takes the machine alone once the one-minute load is under 8.
  • Compiled against JDK 21's API, since this JDK removed Thread.stop, which ScalaTest calls.

Known limits

  • javac does not run. Java sources reach downstream modules as signatures, so Java compile time is missing.
  • A Bloop project lists directories, and two modules' directories hold about 70k lines that sbt does not compile, three files of which do not compile at all. The build uses sbt's own source lists for test modules, so it compiles what the real build does.
  • bal is static: a module keeps its workers until it ends, because a compile cannot yet change its thread count. The largest module depends on many test modules, so it starts when every worker is busy and gets one thread.
  • Warm JVM. A real clean build starts cold, and the first build of a JVM here takes about 75 s against about 65 s warm, at 8×1.
  • One project on one machine. ScalaTest's largest module and its short chain of production modules shape these results.

Still open

  • A real test of workers that move. It needs a compile that can change its thread count, and the model says it would gain little on ScalaTest, though a project with mid-graph chokepoints could differ.
  • A scheduler that reacts to GC load, for its robustness when the heap is badly sized.
  • The square-root heuristic at other core counts and on other projects.
