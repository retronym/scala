# Cake diet: which traits to take out of the compiler cake

## Why

Since JDK 23, HotSpot keeps each class's secondary supers (its interfaces, plus superclasses deeper than the 8-slot primary display) in a hashed table of 63 usable slots (JDK-8180450). Within that size, `instanceof`/`checkcast` against an interface is a hash probe; a class with more falls back to a linear scan. Independently, a megamorphic `invokeinterface` goes through an itable stub that walks the receiver's itable offset table linearly until it finds the interface, so the cost of a call depends on the position of the callee's interface in the receiver class's itable.

Scala 2's cake turns every mixed-in trait into an interface. The audit of the 2.13 class files found `nsc.Global` at 70 secondary supers (20 from the public `reflect.api.Universe`, 39 from traits mixed into `reflect.internal.SymbolTable`, 11 from `nsc.Global`), `interactive.Global` 74, `ReflectGlobal` 81, `JavaUniverse` 71. The analyzer instance has 33 and `Global.erasure` 38, because `Erasure` mixes in all of `Analyzer`. Warm profiles on the scala corpus put about 8% of CPU in itable stubs whose receivers are the analyzer and erasure.

## What the 2025 `cake-diet` branch does

The branch (17 commits, October 2025; `cake-diet-squash` is the same as one commit, and `backup/cake-diet` an earlier copy) takes one trait at a time out of the cake with the same recipe: the trait becomes an `abstract class` with `val self: SymbolTable; import self._`, `SymbolTable` (or `Global`) instantiates it in a `val`, and the handful of entry points used elsewhere get `final def` forwarders or type aliases on the class. Forwarders on the class are free in this respect: they are vtable methods and add no interface. Tiny traits are inlined into a neighbour instead.

| trait | treatment |
|---|---|
| `StdCreators` | `object StdCreators` with the creators typed against `Mirror[_]`/`SymbolTable#Tree` (one macro call site changes) |
| `ReificationSupport`, `TypeDebugging`, `Variances`, `ExistentialsAndSkolems`, `Kinds`, `Internals`, `transform.Transforms` | class in a field of `SymbolTable`, forwarders for `build`, `typeDebug`, `varianceIn*`, `packSymbols`, `existentialTransform`, `internal`, `treeBuild`, `erasure`/`uncurry`/`postErasure`/`transformedType` |
| `tpe.GlbLubs` | class in a private field of `Types`, forwarders for `lub`/`glb`/`weakLub` and the result caches |
| `tpe.CommonOwners`, `CapturedVariables`, `PrivateWithin` | inlined into `Types`, `Symbols`, `SymbolTable` |
| `pickling.Translations` | class in a field, used by the pickler and unpickler |
| `PhaseAssembly`, `DocComments` (nsc) | `PhaseAssembly` instantiated locally when computing phases; `DocComments` an object in `Global` with a `DocComment` alias |

That is 11 interfaces off `SymbolTable`, 2 off `Types`'s closure that also sit on `SymbolTable`, and 2 off `Global`: 15 in all, which takes `Global` from 70 to 55 and `JavaUniverse` from 71 to 58. `interactive.Global` would be 59; `ReflectGlobal` 66, still over.

Status of the commits:

- The 15 "Decake X" commits are the substance and look finished in shape. Each mixes in a little noise (stray blank lines in `Global` and `TypeComparers`, a parameter renamed `default` to `default1` in `AnnotationCheckers`), and `JavaUniverseForce` was edited by hand rather than regenerated by `run/t6240-universe-code-gen`.
- "null!" papers over initialization-order NPEs by making `variances`, `glbLubs` and its `self` lazy. That works, but `lub` and `varianceInType` are warm paths and a lazy val is a volatile read on each access in the runtime-reflection universe. A plain `val` declared early enough (or a field initialised in the trait that first needs it) would avoid both the NPE and the lazy check. The new lazy fields also need entries in `JavaUniverseForce` so runtime reflection initialises them under the lock.
- "Make api.NameApi a trait" is unrelated WIP from the names-out-of-the-cake line of work. It changes a public `reflect.api` class into a trait, which MiMa rejects for 2.13; drop it from this branch.

The branch rebases onto current 2.13.x without conflicts (`cake-diet-rebased`). Build and test results are in the last section.

### Earlier attempts

- `topic/symbol-table-const-pool` (Grzegorz Kossakowski, 2013): "Refactor the cake so SymbolTable does not depend on Global", motivated by unit-testing the symbol table rather than dispatch cost.

## How calls to cake members are compiled

This decides which traits matter, so it comes before the map. A call from code inside a self-typed trait to a member of the cake is emitted against the static type of the receiver, which is the self type:

- In `reflect.internal`, the self type is the class `SymbolTable`. Calls from `Types`, `Symbols`, `Trees` etc. to each other are `invokevirtual SymbolTable.m`, vtable dispatch. In `Types$TypeRef`, `Types$Type` and `TypeMaps$TypeMap` there are 172 such calls and no `invokeinterface` to a cake trait other than `TypesStats`. Across all of `reflect.internal` only a few hundred static call sites are `invokeinterface` on cake traits (`Types` 142, `Definitions` 99, `StdNames` 53, `Names` 43), from inner classes whose outer is typed as the trait (`Types$UniqueType` calls `Definitions.definitions` this way).
- In the typechecker, the self type is the trait `Analyzer`. Every call from `Typer`, `Namer`, `Context`, `Inferencer`, `ImplicitSearch` to its outer analyzer is `invokeinterface Analyzer.m`: 1493 static call sites in `Typers$Typer` alone and 4047 in the `typechecker` package. `Analyzer` is the last entry in the itable of the analyzer instance (28 of 28) and second to last in erasure's (31 of 32), because HotSpot lays out a class's interfaces as the superinterfaces of each local interface first and the local interfaces after them. Each of these calls, when megamorphic, scans the whole table.

So for `Global`, the secondary-super count matters mainly for type checks (`checkcast`/`instanceof` against a cake interface on a 70-entry class is the linear path) and for the minority of `invokeinterface` calls through trait-typed outers. For the analyzer, what matters is that its self type is an interface at all.

## Clusters, ranked

### 1. Make `Analyzer` a class (and give `Erasure` an analyzer instead of being one)

Change `trait Analyzer` to `abstract class Analyzer`. Every `self: Analyzer =>` in the typechecker then names a class, and the 4047 `invokeinterface Analyzer.m` sites become `invokevirtual`, which is vtable dispatch regardless of how many receiver classes there are. This removes the itable scan from the analyzer hot path entirely rather than shortening it, and subsumes caching `global` in a `Typer` field for every other outer member (`newTyper`, `inferImplicit`, `context` helpers, error reporting).

The only thing that stands in the way is `Erasure`, which extends the class `InfoTransform`. It becomes `object erasureAnalyzer extends Analyzer { override def newTyper(c) = new Eraser(c) }` inside `Erasure`, with `Eraser extends erasureAnalyzer.Typer`, plus aliases for `Context`/`Typer` and forwarders for `newTyper`/`rootContextPostTyper` so `Mixin`, `SuperAccessors` and `TypingTransformers` compile unchanged. `InteractiveAnalyzer`, `ScaladocAnalyzer` and `MacroAnnotationNamers` stay traits (a trait may extend a class); `TreeCheckers` and `Duplicators` already extend `Analyzer` as classes.

Interfaces removed: none on `Global`; `Global.erasure` drops from 38 to about 6 (its own transform traits plus `TreeDSL`), and the 33 move to `erasureAnalyzer`, where they no longer matter for dispatch. Churn: two files in the compiler. Risk: low for the compiler itself. For compiler plugins, `new { val global = g } with Analyzer` still compiles; code that extends `Analyzer` in a class that already has a superclass breaks. scala-compiler has no binary-compatibility guarantee across 2.13 releases, and plugins are published per full Scala version.

### 2. Finish `cake-diet` (15 interfaces, Global 70 to 55)

Cheap per trait, and each trait is its own commit. Brings `Global`, `JavaUniverse` and `interactive.Global` under 63, so type checks against cake interfaces on those classes go back to the hashed table, and shortens the itable for the remaining `invokeinterface` calls (the `Types` entry moves from 30 to 28, `Definitions` from 37 to 32). Before merging: replace the lazy vals from "null!" with eagerly initialised fields in the right place, regenerate `JavaUniverseForce`, drop the `NameApi` commit and the whitespace noise.

Binary compatibility: `scala.reflect.internal.*` is excluded from MiMa (`project/MimaFilters.scala`), so removing interfaces from `SymbolTable` is allowed. `JavaUniverse` is in `scala.reflect.runtime` and will need filters for the missing interfaces and the `JavaUniverseForce` methods; both are internal in practice. Macros see `c.universe` typed as `scala.reflect.macros.Universe`, which is untouched. Macros and plugins that call `global.lub` or `global.varianceInType` are compiled as `invokevirtual` on `Global`, so the forwarders keep them linking; only code typed against the internal trait itself (a value of type `reflect.internal.Variances`) breaks, and I found none.

### 3. The next small `SymbolTable` traits (7 more: Global 55 to 48, `ReflectGlobal` 66 to 59)

`TypeToStrings` and `FindMembers` (inline into `Types` or a field), `Collections` (an import of the existing `object Collections`; mechanical but touches about 80 files), `InfoTransformers`, `AnnotationCheckers`, `Importers` and `FreshNames` (class in a field with type aliases and forwarders). This is what brings `ReflectGlobal`/`ToolBoxGlobal` under 63. Same compatibility story as cluster 2, except that `AnnotationChecker` and `InfoTransformer` are extended by plugins and phases and need type aliases that remain extendable.

### 4. `nsc.Global`'s own movable traits (3: `Plugins`, `Parsing`, `ast.Positions`)

Small, independent, one forwarder each. Worth doing alongside cluster 3, mostly for `ReflectGlobal` and `interactive.Global`.

### 5. Shrink `Analyzer` (up to 16 interfaces)

The splain cluster (5) and the macro-runtime cluster (4) are the clean ones: cold code, a few call sites, reachable through one object field. The helper traits (`EtaExpansion`, `Unapplies`, `NamesDefaults`, `SyntheticMethods`, `TypersTracking`, `ImportTracking`, `TreeDSL`) can follow one at a time. If cluster 1 lands, this is housekeeping: the analyzer has no `invokeinterface` hot path left to shorten and is well below 63. If cluster 1 is rejected, these 11 cold interfaces are exactly the ones that sit in front of `Contexts`, `Typers` and `Analyzer` in the itable, so removing them is the next best thing.

### Not worth it

The 20 `reflect.api` interfaces are public API under MiMa. `TypeComparers`, `TypeMaps`, `TypeConstraints`, `BaseTypeSeqs`, `StdAttachments` and the universe-defining traits either carry the universe's types or are the hottest code, where a field load per call would cost more than the interface does. A deeper class chain does not help either: `Global` is at depth 5 and its subclasses at 6 and 7, so only one primary slot is free.
