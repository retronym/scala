Every tree pays 2428 bytes before its own fields

The base is the object header plus four 4-byte fields: $outer (in TreeContextApiImpl, the cake's SymbolTable), id, rawtpe and rawatt. Objects round up to 8 bytes, so a field only saves memory when it removes a padding slot, and only costs memory when it needs a new one. With the 8-byte header, a class with an even number of fields has no padding.With the 12-byte header, a class with an odd number of fields has no padding.

The three candidates, scala corpus

Live tree bytes under each change, against today's layout with the same header.

  • A, drop id: −9.1%−11.5%. Classes with an odd field count lose their padding and shrink by 8: Select 40→32, ValDef 48→40, DefDef 56→48, Literal and New 32→24, CaseDef, If, Bind, Function. Ident, TypeTree, Apply and This are already full at 32 and gain nothing.
  • B, symbol on every tree: +7.0%+1.2%. SymTrees are unchanged. Non-SymTrees with an even field count need a new slot: TypeTree, Apply, TypeApply, Block and AppliedTypeTree grow 32→40. Literal, New, CaseDef and If take the field into their padding.
  • A + B: −7.8%−5.3%. B gives back only 1.4 points of A's saving. TypeTree, Apply and Select all end at 32; the classes that lose A's saving are the odd-count non-SymTrees such as Literal (back to 32) and CaseDef (back to 40).
  • C, drop $outer (reference only): −9.1%−11.5%, the same slot effect as A. A+B+C reaches −15.1%−18.4%. Tree methods reach the universe through the outer, so this would need them to get it another way.
  • A, drop id: −9.1%−11.5%. Every class with an even field count (TypeTree, Apply, Ident, This, TypeApply, Block, …) loses its padding and shrinks 40→32. Select, ValDef, DefDef and Literal already fill their last slot and gain nothing.
  • B, symbol on every tree: +7.0%+1.2%. SymTrees are unchanged; the non-SymTrees with a padding slot take the field for free, and Literal, New, CaseDef, If and Throw grow by 8.
  • A + B: −7.8%−5.3%. B uses the slot that A frees: against A alone it gives back 6.2 points, since TypeTree and Apply return to 40.
  • C, drop $outer (reference only): −9.1%−11.5%, the same slot effect as A. A+B+C reaches −15.1%−18.4%. Tree methods reach the universe through the outer, so this would need them to get it another way.

Positions

Positions take about half as many bytes as trees. RangePosition holds a source reference plus start, point and end; OffsetPosition a source and point. Trees often share a position object (copyAttrs, focus), so there are fewer positions than trees. SingleAttachment wraps a position when a tree carries an attachment.

headerfieldalignment padding

With compact headers every position and attachment class has an even field count, so none carries padding: OffsetPosition is 16 B and RangePosition 24 B. A field added to a position would cost 8 bytes; removing one would save nothing. TransparentPosition adds no fields to RangePosition.

With 12-byte headers every position and attachment class carries 4 bytes of padding: OffsetPosition is 24 B and RangePosition 32 B. A field added to a position would cost nothing; removing one would save 8 bytes. Compact headers remove the padding and save 8 bytes on each, about 8.8 MB on the scala corpus. TransparentPosition adds no fields to RangePosition.

  • S1, drop Symbol.initName. The constructor parameter is kept as a field because sealedSortName reads it. That method orders sealed children for the pickler and for exhaustivity checking. Both run before names are expanded, so rawname may give the same order. This still needs checking.
  • S2, move javaBinaryNameStringCache to ClassSymbol. No symbol has it set after typer. It is read for classes and modules, by the pickler's .sig writer and by the backend, and a module could compute it from its module class.
  • S3, inline the head of the type history. Every symbol owns one TypeHistory, and none has a _prev after typer. Storing the info, its valid-from period and the previous entry on the symbol adds 8 bytes to every symbol and removes a 2432 byte object. Later phases add history entries, which would still be separate objects.
  • S4, move TermSymbol._referenced to ModuleSymbol. Every module sets it, to its module class. Only 0.1% of other term symbols and 2.8% of method symbols set it after typer, mostly default getters. Later phases set it on accessors and outer fields, which could use an attachment.
  • T1, move the TypeRef parents cache to a side table. parentsCache and parentsPeriod are set on 0.2% of ClassArgsTypeRef and 1.7% of ClassNoArgsTypeRef. Removing both saves 8 bytes on every TypeRef with either header.
  • T2, allocate BaseTypeSeq.pending lazily. Every base type sequence allocates a BitSet and its long[]. These are only used while a lazy intersection element is being computed. The figure assumes none is needed, so it is an upper bound.
  • N1, drop Name.cachedString. Set on 2.5% of names. It only saves memory with compact headers, and names are small: 53k names in 1.7 MB.
  • X, drop the cake $outer from symbols, types, names and type histories, for reference only, like C for trees.

Where one field makes a difference

With compact headers, TermSymbol and MethodSymbol carry 4 bytes of padding, so S1, S2 or S4 alone shrinks them by 8 bytes. Type symbols and modules have none.With 12-byte headers, TermSymbol and MethodSymbol have no padding, so a single dropped field saves nothing on them, and S1 or S2 alone only helps type symbols and modules. ClassArgsTypeRef holds ten 4-byte fields and a 1-byte trivial flag. With compact headers the flag is the one byte that pushes it from 48 to 56.With 12-byte headers it has 3 bytes of padding, so only dropping two fields (T1) shrinks it.

Name table

A Name is an offset and length into one shared char[], plus a hash chain link, a cached string and the cake $outer. The table holds 594,751 characters in a 1M-character array, which has doubled from its initial 128k. Names and the table together take 44 MB, so no change here is worth much.

Notes for B beyond footprint

  • Non-SymTrees with a symbol override delegate rather than store: Apply/TypeApply → fun.symbol, Super → qual.symbol, AppliedTypeTree → tpt.symbol, TypeTree → typeTreeSymbol, ReferenceToBoxed, and nsc's DocDef. A field read in Tree only replaces the virtual call if these cache the delegate's symbol (setters already write through, but TypeTree's depends on tpe) or keep an override, which leaves the call site polymorphic.
  • Apply and TypeApply are 11.7% of tree count, and both are among the classes B grows when no padding slot is free.
  • id readers are diagnostics only: position validation errors (Positions.scala), TreeBrowsers, and the tree printer's enclosing-tree prefix. An identity map built when the error is reported serves all of them.

Method

  • Compile each corpus with -Ystop-after:typer in one JVM, holding the Run, then take a live class histogram (GC.class_histogram, after full GC). Corpora: compiler-benchmark scala (library, reflect and compiler, 1135 files, library on the sourcepath), scalap, re2s. All compile without errors. The live heap after typer on the scala corpus was 333 MB with 12-byte headers, trees 19.7% of it and positions 9.7%.
  • The heap counts all live trees: 1.69M for scala. An identity-deduplicated walk of unit bodies (including TypeTree.original) reaches 1.33M; the rest are held outside unit bodies, for example by symbols' completers and annotations. Weighting by the walk instead gives the same percentages within 0.3 points.
  • Tree sizes per scenario: JOL 0.17 field list per class, 4-byte compressed references, header 12 or 8, rounded up to 8. With only 4-byte and 1-byte fields this rule is exact under JDK 15+ field layout.
  • Symbol, type, name and scope sizes come from a model of HotSpot's JDK 15+ field layout, applied class by class from Object down. Primitives are placed largest first, then references. Each field goes into the smallest gap that fits it at its natural alignment, left by the header or a superclass, or else at the end. This matters for the 8-byte _rawflags and for 1-byte flags.
  • Each corpus was also run with -XX:+UseCompactObjectHeaders. The modelled sizes match the histogram's bytes per instance for every class, trees included, with both header sizes.
  • Field use comes from a reflective, identity-deduplicated walk of everything reachable from Global, run after the histogram. Its instance counts match the histogram for every symbol, type, name and scope class. Array bytes are summed per owning field, and for the type and scope arrays they match the histogram.
